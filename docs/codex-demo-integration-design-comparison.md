# Codex 계획 기록 — 두 데모의 융합 아이디어·설계 비교

작성일: 2026-09-26 (KST)  
작성 주체: Codex, 사용자와의 계획 대화 정리  
상태: **설계 비교용으로 종료 — 구현 계획 실행 대상 아님**

## 1. 이 문서의 목적과 최종 결정

원래는 `mes-assistant-platform`의 데모를 완성하기 위해 `mes-assistant-platform2`의 기능 아이디어를 중심으로 두 프로젝트의 장점을 융합하려고 했다. 파일 업로드와 대화 간 컨텍스트 활용을 먼저 평가하고, UI·UX 개선, 향후 DB 연결을 위한 데이터 정리, 문서화를 함께 진행하는 계획이었다.

계획 수립 이후 사용자는 **구현하지 않고, Codex에서 계획한 내용을 다른 에이전트가 참고할 아이디어·설계 비교용 문서로만 남기는 것**으로 작업을 마무리했다.

따라서 아래 내용은 구현 현황이나 실행 승인, 후속 작업 지시가 아니다. 새로운 사용자 요청 없이 브랜치 생성, 기능 구현, 데이터 마이그레이션, 테스트 환경 구축을 시작하지 않는다. 원래 제안한 브랜치명 `codex/demo-context-integration`도 계획 기록일 뿐이며, 이 문서 작업에서는 생성하지 않았다.

### 비교 대상과 읽기 순서

- 현재 저장소: `mes-assistant-platform` — Codex 작업 기반.
- 형제 저장소: `mes-assistant-platform2` — 사용자 표현상 Claude 작업 기반이며, 기능 아이디어의 주된 참고 대상.
- 실제 구현의 시작점은 현재 저장소의 [HANDOFF.md](../HANDOFF.md)와 형제 저장소의 `docs/HANDOFF.md`다. 이후 관련 소스와 현재 Git 상태를 확인한다.
- 기존 [comparison-platform2.md](comparison-platform2.md)는 2026-09-22의 과거 구조를 다룬다. 거기에 적힌 결함·저장 방식·패키지 모델을 현재 상태로 단정하지 않는다.
- 이 문서는 당시 handoff 및 일부 핵심 코드를 읽은 결과다. 이번 계획 대화에서 앱을 브라우저로 비교하거나 테스트·빌드·실제 API 검증을 실행하지 않았다.

## 2. 사용자와 확인한 의도 및 설계 선택

아래는 계획 대화에서 사용자가 직접 요청하거나 선택한 내용이다. 최종 결정은 이 아이디어를 **참고용으로 보관**하는 것이므로, 설계 선택에 대한 동의와 구현 승인을 혼동하지 않는다.

| 항목 | 확인한 내용 |
|---|---|
| 중심 아이디어 | 기능은 platform2의 아이디어가 주된 기준이다. |
| 원래 작업 순서 | 파일·공유 컨텍스트 기능 평가를 선행하고 UI·UX, DB 친화적 정리, 문서화를 진행하려 했다. |
| 느슨한 연결 | 단계나 순서를 참조 판단 요소로 사용하고 싶지 않다. 고정 워크플로우를 만들지 않는다. |
| 대화 후보 | 같은 태그를 직접 공유하는 대화 안에서만 선택한다. 전체 대화 검색이나 AI 추천으로 범위를 넓히지 않는다. |
| 기본 조작 | 첨부파일처럼 대화도 통으로 체크할 수 있고, 세부 제어 옵션을 제공한다. |
| 원문 전달 | 대화 체크 시 전체 원문을 기본으로 전달한다. 길이 한도 초과 시 요약 또는 메시지 범위 선택을 안내한다. |
| 자동 축약 | 자동으로 원문을 잘라내거나 요약해서 보내는 방식은 채택하지 않는다. |
| 검증 범위 | 모의 API 검증과 실제 환경용 검증 절차 준비까지를 선택했다. 실제 OpenWebUI 연동 성공은 완료 조건으로 삼지 않았다. |
| UI 개편 범위 | 홈·칸반 → 대화·자료 선택 → SR 접수·결과 공유의 주요 사용 흐름 전체. 관리·설정·리포트는 필요한 부분만 조정한다. |
| 백엔드·DB | 실제 백엔드 및 서버 DB 연결은 향후 별도 프로젝트다. |
| 최종 마무리 | 기능을 구현하지 않고 설계 비교용 문서로만 남긴다. |

초기에는 Codex가 ‘인계 요약’을 제안했으나, 사용자는 순서를 전제로 하는 표현과 별도의 요약 전달 절차보다 **같은 태그의 대화를 파일처럼 선택하는 방식**을 원했다. 후속 독자는 초기 제안을 최종 사용자 요구로 되돌리지 않도록 주의한다.

## 3. 비교에서 얻은 융합 아이디어

Codex의 추천은 **platform2의 주요 화면·사용 흐름을 현재 repo에 점진적으로 반영하면서, 현재 repo의 저장·요청 보호 기능을 유지하는 것**이었다. 이는 전체 소스 교체나 형제 저장소의 Git 이력 병합을 뜻하지 않는다.

| 영역 | 관찰 또는 참고점 | 당시 제안 |
|---|---|---|
| 대화 화면 | platform2는 가운데 채팅과 오른쪽 자료·체크·노트·이력 패널, 좁은 화면의 탭 전환으로 구성한다. | 대화 중심 레이아웃과 주요 탐색 흐름을 참고한다. |
| 관련 대화 | platform2의 관련 대화 표시는 같은 태그의 대화로 이동하는 기능이다. | 이동 기능과 별개로 대화 내용을 AI 입력으로 체크하는 기능을 설계한다. |
| 플랫폼 컨텍스트 | platform2는 주 입력, 출처, 연결 SR 등의 정보를 프롬프트에 표현한다. | 현재 repo의 전달 기록과 결합하되 업무 역할 지침을 주입하지 않는다. |
| 파일 전달 | 확인한 platform2 코드는 업로드 실패를 수집하고 호출 측이 텍스트로 대신 전달하는 구조다. 현재 repo는 처리 완료를 기다리고 실패 시 요청을 중단한다. | 현재 repo의 명시적 실패·재시도·전달 방식 선택을 유지한다. |
| 요청 보호 | 현재 repo는 요청 시점 스냅샷, 실행 임대, 복원 epoch 검사 등을 갖는다. | UI 개편 과정에서 우회하거나 제거하지 않는다. |
| 유지보수 | platform2는 기능·도메인·DB·LLM 계층이 구분되어 있다. | 필요한 화면과 신규 컨텍스트 로직부터 책임을 분리한다. |

위 관찰은 당시 읽은 코드에 한정한다. 형제 저장소 전체의 품질이나 기능 우열을 검증한 결론은 아니다.

## 4. 당시 Codex가 제시한 구체 설계안

이 절에는 사용자 선택을 바탕으로 Codex가 추가한 구현 제안과 기본값도 포함되어 있다. 모든 세부 규칙을 사용자가 개별 확정한 것은 아니다.

### 4.1 기능 평가 선행

- 가상 자료와 모의 API로 업로드 → 자료 발견 → 선택 → 요청 포함 → 답변 저장 → 다른 대화에서 재사용하는 흐름을 평가한다.
- 파일별 업로드·처리 완료·실패·취소·재시도와 복수 파일 전달을 확인한다.
- 선택하지 않은 자료 제외, 주 입력 표시, 출처, 버전 고정, 요청 중 선택 변경을 확인한다.
- 현재 handoff에 기록된 OpenWebUI 주 입력 의미 전달 누락을 보완 후보로 삼는다. 전송 당시 로컬 파일 버전과 원격 파일 ID의 대응 기록도 검토한다.
- 파일 전달 실패 시 전송을 멈추고 사용자가 재시도·제외·텍스트 전달 중 선택하게 한다.
- 요청 구성이 올바른지와 실제 모델이 자료를 이해했는지는 별도 평가한다. 후자는 실제 환경용 자료·질문·예상 근거·판정 기준을 준비하는 데 그친다.

### 4.2 대화 컨텍스트 선택

- 자료 패널에 파일 / 대화 목록을 제공하고, 입력창 근처의 ‘이번 요청에 사용’ 영역에 선택 항목을 함께 표시한다.
- 같은 태그를 직접 공유하고 열람 가능한 다른 대화만 후보로 표시한다. A–B, B–C 연결만으로 A에서 C를 자동 발견하지 않는다.
- 대화 체크 시 선택 시점의 전체 AI 대화 원문을 기본 입력으로 삼는다. 팀 의견, 시스템 지침, 실패·미완성 응답은 제외하는 안을 제시했다.
- 세부 옵션은 전체 원문 / 선택 메시지 / 요약으로 구성하고 전달 내용 미리보기를 제공한다.
- 참조 대화는 현재 대화의 발화로 합치지 않고 출처가 있는 참고 데이터로 구분한다.
- 원본 대화가 사용했던 파일, 요청 스냅샷, 다른 참조 대화를 재귀적으로 수집하지 않는다. 필요한 파일은 별도로 선택한다.
- 선택 시점의 내용을 고정하고 새 메시지가 생기면 ‘업데이트 있음’과 명시적 갱신을 제공하는 안을 제시했다.
- 태그 해제 후 기존 선택은 파일과 일관되게 유지하면서 연결 해제를 표시하되, 전송 시 열람 가능 여부를 다시 검사하는 안을 제시했다.
- 요청 시작 시 사용 내용·출처를 고정해 기록한다. 선택 해제나 갱신은 이후 요청부터 반영한다.

태그는 자료 발견 조건이며 권한 자체가 아니다. 또한 재귀 수집을 막더라도 B의 답변 본문에 C에서 얻은 내용이 이미 포함될 수 있다. 이 설계는 그러한 간접적인 내용 전파까지 제거하거나 정보 출처를 완전히 증명하는 기능을 의미하지 않는다.

### 4.3 길이 한도와 요약

- 현재 연결 프로필의 요청 크기 제한을 활용하고, 전송 전에 크기와 초과 여부를 안내한다.
- 한도를 넘으면 전송을 막고 요약·메시지 범위 선택·입력 해제를 안내한다. 자동 절단·자동 요약은 하지 않는다.
- 요약은 사용자가 선택한 별도 보조 요청으로 생성하고 확인·수정 후 적용한다.
- 요약 요청 자체가 한도를 넘으면 메시지 범위를 줄이도록 안내한다. 자동 분할 요약 파이프라인은 이 안에 포함하지 않았다.

당시 확인한 현재 repo는 `maxRequestBytes`와 기본값 262144 바이트를 사용했다. 이는 모델의 토큰 한도와 다르다. 요청 바이트 제한을 통과했다고 모델 컨텍스트 한도까지 보장한다고 설명하면 안 된다. 모델별 토큰 예산 정책은 이 계획에서 확정하지 않았다.

### 4.4 주요 UI·UX

- 홈·칸반, 대화·자료 사용, SR 접수·결과 공유를 일관된 흐름으로 정리한다.
- platform2의 대화 중심 레이아웃을 참고하고 좁은 화면은 탭으로 전환한다.
- 파일·대화에 선택·해제·주 입력·출처 확인의 공통 패턴을 적용한다.
- 업로드 중, 처리 중, 선택됨, 전송 실패를 구분하며 오류 해결 동작을 해당 항목 가까이 배치한다.
- 빈 화면, 긴 제목, 다수 태그·파일·대화, 키보드 조작, 한국어 입력을 점검한다.
- 실제 화면 비교와 대표 과업 수행으로 입력 포함 여부의 혼동과 불필요한 화면 이동이 줄었는지 평가한다.

구체적인 시각 디자인, 컴포넌트 라이브러리 교체, CSS 체계 전환은 확정하지 않았다. platform2 참고가 그 저장소의 모든 의존성을 가져온다는 뜻은 아니다.

### 4.5 향후 DB 연결을 위한 데이터 정리

기존 IndexedDB와 사용자 데이터를 유지하며 다음 경계를 제안했다. 아래 이름은 설계상 후보이며 기존 타입이나 확정된 API 계약이 아니다.

| 제안 모델 | 역할 |
|---|---|
| `ConversationInput` | 대상 업무, 원본 대화, 전달 방식, 고정 컨텍스트 참조, 주 입력 여부, 선택자·시각 |
| `ContextSnapshot` | 원본 메시지 참조, 고정 내용, 요약 및 수정 출처 |
| `RequestRecord` 확장 | 실제 사용한 파일 버전·대화 스냅샷·전달 결과 기록 |

- UI는 서비스·저장 인터페이스를 통해 변경하며 신규 직접 저장 경로를 늘리지 않는다.
- 영속 업무 데이터, 파일 본문, 사용자 화면 설정, 임시 실행 상태를 구분한다.
- API 키와 재사용용 원격 캐시는 영속·백업 대상에서 제외한다. 전송 당시 원격 파일 식별 기록은 재사용 캐시와 구분한다.
- 새 데이터가 생기는 경우 마이그레이션·백업·복원·참조 무결성을 함께 다룬다. 기존 브라우저 데이터를 초기화하지 않는다.
- 실제 서버, DB 엔진, 인증·SSO, 다중 PC 동기화, 서버 권한 강제는 별도 프로젝트다.

구체적인 테이블 DDL, DTO, HTTP API, 삭제 정책, 전체 스키마 정규화 범위는 확정하지 않았다. 기존 `WorkItem`·`Conversation` 등 타입을 무조건 교체하려는 계획도 아니다.

## 5. 계획했던 검증과 문서 산출물

### 검증 시나리오 — 아직 실행하지 않음

- 같은 태그의 파일·대화가 후보에 나타나고 선택한 항목만 요청에 포함되는지.
- 간접 태그 연결, 자기 대화, 상호 참조가 자동 확장이나 중복 첨부를 일으키지 않는지.
- 전체 체크, 메시지 선택, 요약 적용, 선택 해제, 갱신이 실제 요청 내용에 반영되는지.
- 길이 초과·업로드 및 처리 실패·요약 실패·취소 시 입력과 기존 선택을 보존하는지.
- 요청 도중 원본 변경, 태그 해제, 역할 변경, 백업 복원에도 기록과 공개 범위를 보존하는지.
- SR 공유, 완료 잠금·재개, 다중 탭, 백업·복원 회귀 테스트 및 빌드가 통과하는지.

### 구현했을 경우 준비하려던 문서

- 융합 설계: 채택 기능, 프로젝트 간 차이를 해소한 결정, 대화 컨텍스트 규칙.
- 기능 평가: 재현 절차, 모의 검증 결과, 실제 환경 평가 자료와 미검증 항목.
- 데이터 계약: 영속 대상, 관계·제약, 파일 저장 경계, 향후 백엔드 전환 지점.
- 시연·handoff: 실행법, 대표 시나리오, 구현 상태, 남은 과제.

당시의 목표는 파일과 대화를 선택해 활용하고 **무엇이 실제 요청에 사용됐는지 추적할 수 있는 데모**였다. 이 목표는 달성 결과가 아니며, 이번 작업은 이 문서와 탐색용 handoff 링크를 남기는 것으로 종료한다.

## 6. 이 문서를 읽는 다른 에이전트에게

1. **비교 자료로만 읽는다.** 사용자 최종 요청은 문서화 후 종료다. 이 문서를 발견했다는 이유로 구현을 재개하지 않는다.
2. **구현 상태의 근거를 분리한다.** 기존 handoff의 과거 검증 기록, 이번 코드 관찰, 사용자 선택, Codex의 제안은 서로 다르다. ‘제안됨’을 ‘구현됨’이나 ‘테스트 통과’로 바꾸지 않는다.
3. **실제 코드가 우선이다.** 현재 repo는 이미 과거 계획의 일부를 구현했다. 새 요청이 생기면 양쪽 저장소의 최신 상태를 다시 확인하고 중복 구현을 피한다.
4. **사용자 정정을 보존한다.** 순서 기반 인계, 강제 단계, 자동 후속 실행을 도입하지 않는다. 같은 태그 안에서 대화를 통으로 체크하고 필요할 때 세부 조절한다는 의도가 핵심이다.
5. **선택 스냅샷 정책은 제안으로 취급한다.** 고정 시점, 태그 해제 후 유지, 요약 확인 절차 등은 Codex가 제시한 기본값이다. 이후 상충하는 사용자 요구가 나오면 이 문서를 고정 계약으로 주장하지 않는다.
6. **형제 repo 전체를 그대로 복사하지 않는다.** 파일 실패 처리, 저장 정책, 공개 범위, 태그 정규화 등 양쪽 구현 차이를 확인해야 한다. 소스 이력이나 민감한 시드 데이터를 무심코 가져오지 않는다.
7. **자료 노출 범위를 지킨다.** 실제 사내 주소·키·참고 이미지·사용자 백업을 비교 문서나 테스트 fixture에 넣지 않는다. 요청자에게 공유된 결과를 볼 수 있다는 이유로 내부 대화 원문까지 노출하지 않는다.
8. **이 문서는 완성된 실행 명세가 아니다.** 구현으로 재개한다면 현재 요청과 사용자 의도를 기준으로 미확정 정책을 정리하고 별도의 실행 계획을 만든다. 이 문서의 예시 타입·브랜치명·검증 목록만으로 작업을 자동 수행하지 않는다.
