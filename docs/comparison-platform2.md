## 1. 결론과 범위

**현재 데모의 컨텍스트·공개 범위 모델을 유지하고, platform2의 저장 계층·대화 UX·재사용 탐색·리포팅 구조를 선택적으로 도입하는 것이 좋다.**

- A: `D:\_Repositories\mes-assistant-platform\agent-hub-demo` — 이번에 구현한 새 데모. 상위 저장소의 예전 워크플로우 앱은 비교 대상에서 제외했다.
- B: `D:\_Repositories\mes-assistant-platform2` — 비교 데모.
- 소스, 데이터 구조, README, 자동 테스트 및 빌드를 확인했다. 이번 비교에서 B의 브라우저 화면을 직접 조작하거나 사내 API에 접속하지 않았다. UI 평가는 구현된 화면 구성·상호작용 기준이며 시각적 품질의 직접 비교는 아니다.
- 두 프로젝트의 출발 프롬프트가 완전히 같다는 전제는 두지 않는다. B의 차이 중 일부는 버그가 아니라 다른 제품 선택이다. 적합성 판단 기준은 현재 대화에서 승인한 Agent Hub 설계다.

## 3. A에서 우선 수정할 사항

### P1-1. 여러 탭에서 변경 내용이 덮어써짐 — 동작 재현

근거: [store.tsx](../src/store.tsx:21), [domain.ts](../src/domain.ts:47).

각 탭은 최초 로드한 상태를 메모리에 들고, 모든 변경마다 전체 상태를 localStorage에 쓴다. 다른 탭의 변경을 받는 구독이나 충돌 검사가 없다.

재현: 같은 초기 상태에서 탭 A가 URS 메모를 저장하고 탭 B가 FDS 메모를 저장하면 B의 전체 상태에 A의 메모가 없으므로 사라진다. 두 독립 상태 스냅샷을 이용한 임시 검증에서 이 손실을 확인했다. 실제 두 브라우저 탭 UI를 통한 재현은 하지 않았다.

제안: B의 엔티티별 IndexedDB repository + transaction + liveQuery 구조를 도입한다. 사용자는 sessionStorage로 탭별 분리한다. 단순 storage 이벤트 추가만으로 동시 쓰기 충돌이 해결되지는 않는다.

인수 기준: 두 탭이 서로 다른 업무/같은 업무의 메모를 추가해도 모두 남고, 상대 변경이 자동 표시된다.

### P1-2. 응답 대기 중 컨텍스트 제거 시 이미 보낸 요청의 기록이 거절됨 — 동작 재현

근거: [Workspace.tsx](../src/Workspace.tsx:137), [domain.ts](../src/domain.ts:316).

사용자 메시지와 응답을 API 성공 후에 저장한다. 그 사이 활성 컨텍스트를 제거하면 message.add가 과거 전송 contextIds를 현재 activeBundleIds와 비교해 거절한다. UI의 컨텍스트 제거 버튼은 응답 중에도 사용 가능하다.

재현: 컨텍스트 선택 → 요청 당시 ID 보관 → 컨텍스트 제거 → 당시 ID로 메시지 저장 시 ‘비활성 컨텍스트’ 오류. 이 도메인 경로를 임시 테스트로 확인했다. 실제 느린 API와의 UI 재현은 하지 않았다.

제안: 전송 시작 시 RequestRecord를 먼저 만들고 requestId·모델·전송 시각·스냅샷을 고정한다. 성공/실패/취소는 해당 요청에 연결한다. 현재 활성 컨텍스트는 다음 요청에만 영향을 준다. 사용자 메시지+응답 상태 변경도 원자적으로 처리한다.

인수 기준: 응답 도중 칩 제거·화면 이동·역할 변경·API 실패가 발생해도 이미 보낸 요청의 기록이 정확히 남고, 공개 범위는 바뀌지 않는다.

### P1-3. 긴 자료의 중복 저장과 무제한 요청 크기

근거: [api.ts](../src/api.ts:10), [Workspace.tsx](../src/Workspace.tsx:104), [store.tsx](../src/store.tsx:40).

텍스트 파일은 Blob 외에 content에도 저장하고, 매 요청의 전체 대화/파일 내용을 requestSnapshot 문자열로 다시 보관한다. 길이·총 토큰 제한 없이 전송하며 매 변경마다 전체 상태를 복제하고 직렬화한다. 반복 대화에서는 저장 용량과 UI 지연이 커질 가능성이 높다. 용량 한계/성능 수치는 실측하지 않았다.

제안: 원본과 요청 스냅샷을 IndexedDB로 이전하고, 불변 버전 참조로 중복을 줄인다. 전송 자료 선택·예상 크기·총 문맥 예산·초과 안내를 제공한다. B의 12,000자 단순 절단을 그대로 가져오면 누락을 알기 어려우므로 잘린 범위와 사용자 확인이 필요하다.

### P2-1. 완료 상태의 변경 정책이 불완전 — 동작 재현

근거: [domain.ts](../src/domain.ts:239), [Workspace.tsx](../src/Workspace.tsx:736).

완료→진행 상태 변경에는 사유가 필요하지만 완료 상태에서 체크리스트를 해제하는 것은 가능하다. 임시 테스트에서 상태는 done인 채 체크가 false로 바뀌는 것을 확인했다. 활동은 기록되므로 완전한 무기록 수정은 아니다.

제안: 정책을 명확히 정한다. 완료 당시 산출물/체크리스트를 고정하고, 수정하려면 사유 있는 재개 또는 별도 후속 업무를 사용한다. B는 완료 화면의 일부 컨트롤을 readOnly로 처리하지만 저장 계층까지 같은 정책인지 별도 검토해야 한다.

### P2-2. 기간 리포트가 해당 기간의 실적과 다를 수 있음

근거: [App.tsx](../src/App.tsx:193).

기간은 업무 updatedAt에만 적용하고, 선택된 업무의 인계·활동은 전체 기간으로 집계/내보낸다. 과거 완료 업무에 오늘 메모만 남겨도 최근 기간의 완료 수에 포함될 수 있다. 참여자 필터 역시 해당 기간의 기여 횟수가 아니라 과거 참여 여부다.

제안: completedAt과 구조화된 활동 이벤트를 추가하고, 완료/인계/참여 지표마다 해당 이벤트 시각으로 필터링한다. B의 reporting.ts처럼 순수 집계 함수와 테스트를 분리한다. 최근 24시간/7일과 달력 기준 일/주도 구분한다.

### P2-3. 업로드와 AI 입력 선택을 분리

근거: [api.ts](../src/api.ts:27), [Workspace.tsx](../src/Workspace.tsx:395).

현재 입력 자료는 모두 요청에 들어간다. 제외하려면 업무의 파일 연결을 제거해야 하므로 보관할 자료와 이번 AI가 볼 자료가 결합되어 있다.

제안: 파일은 자료함에 계속 남기고 대화별 selectedInputIds로 전송 여부를 선택한다. B의 InputFilePicker UX를 참고한다. 기존 컨텍스트 칩과 함께 ‘이번 요청에 포함할 내용’을 미리 보여준다.

### P2-4. 백업 복원과 오류 복구 경로 추가

근거: [export.ts](../src/export.ts:42), [store.tsx](../src/store.tsx:21), [files.ts](../src/files.ts:10).

현재는 업무별 검토 자료를 내보낼 수 있으나 앱 전체 상태를 복원할 수 없다. 저장 데이터 초기화 시 검증도 version과 agents 배열 정도이며 파싱 오류에서는 seed로 넘어간다. Blob 저장 후 메타데이터 저장 실패 시 고아 파일이 생길 수 있다.

제안: 전체 백업·가져오기 미리보기·스키마 검증·참조 무결성 검사·마이그레이션·롤백을 추가한다. 파싱 오류는 사용자에게 알리고 원본 데이터 다운로드를 제공한다. 키는 어떤 백업에도 넣지 않는다.

### P2-5. AI 연결 진단과 실패 UX

근거: [AgentAdmin.tsx](../src/AgentAdmin.tsx:498), [api.ts](../src/api.ts:96).

모델 목록 경로를 편집하지만 실제 목록 조회에 사용하지 않는다. 연결 테스트·스트리밍·사용자 취소·실패 메시지 상태·명시적 재시도도 없다. 오류 토스트가 사라지면 실패 원인을 다시 확인하기 어렵다.

제안: B의 Provider 인터페이스와 SSE/중지/연결 진단 UI를 참고하고, A의 모델·출처·스냅샷 기록을 유지한다. 목록 조회 성공과 실제 대화 성공은 별도로 확인한다.

### P3. 화면과 코드 구조 개선

- 패키지 보관함에 해당하는 ‘컨텍스트 보관함’: 원본/버전/수신처/연결 해제 상태 검색, 현재 업무로 재사용.
- Workspace를 ChatPanel, ArtifactPanel, ContextPanel, WorkDetails, ShareDialog로 분리. App의 SR/리포트/시스템 assistant도 독립 모듈로 분리.
- window.prompt를 입력 검증이 있는 공통 대화상자로 교체. 업무 설정은 매 글자마다 저장·활동 생성하지 않고 편집 초안→저장으로 처리.
- 응답을 안전한 Markdown으로 렌더링해 URS/FDS 표와 목록 가독성 개선. 원시 HTML 실행은 허용하지 않는다.
- 시스템 assistant는 자연어→구조화된 제안→미리보기→공통 도메인 명령 실행으로 확장. 결과 생성뿐 아니라 컨텍스트 정리·SR 연결도 지원.

## 5. 권장 적용 순서

| 순서 | 묶음 | 완료 기준 |
|---|---|---|
| 1 | 요청 상태·전송 스냅샷·완료 정책 | 응답 중 컨텍스트 변경과 실패/재개 회귀 테스트 통과 |
| 2 | IndexedDB 저장 계층·탭별 사용자·트랜잭션·백업 | 동시 저장 손실 없음, 파일 포함 백업 복원, 키 제외 |
| 3 | 자료 입력 선택·연결 진단·스트리밍·취소 | 선택 자료만 전송, 실패/취소 기록 보존, 실제 모델 추적 |
| 4 | 컨텍스트 보관함·이벤트 기반 리포트·피드백 | 해제된 자료 재사용, 기간별 실적 정확, 개선 자료 추출 |
| 5 | 화면 분리·Markdown·시스템 assistant 확장 | 작은 화면/키보드 사용성과 주요 사용자 흐름 UI 테스트 |

권장 방식은 전면 재작성보다 저장/요청 경계를 먼저 추출하는 점진적 개선이다. ContextBundle, ArtifactVersion, Handoff, SharedResult는 현재 의미를 보존한다.
