# Task 모듈 기반 업무와 사내 API 연결

## 1. 정보 구조

| 단위                  | 책임                                                                   | 변경 영향                                                                    |
| --------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| TaskModule            | 재사용 업무 정의, assistant, 기본 모델, 달성 체크리스트                | 이름/체크리스트/방식은 새로 추가하는 Task에 복사. 모델 기본값은 실행 시 상속 |
| Template              | Task 정의의 순서와 조합                                                | 새 업무에 적용. 기존 업무는 유지                                             |
| Work                  | 실제 업무, 담당자, 외부 ID, Task 인스턴스                              | 업무별 구성을 독립 편집                                                      |
| Stage (Task 인스턴스) | 진행 상태, 체크리스트, 파일 참조, 메모, 대화방                         | 고유 ID로 대화/자료 보존. API 필드명 Stage는 기존 데이터 호환을 위해 유지    |
| ChatThread            | 독립 대화방과 모델 선택                                                | 같은 Task 안에서도 이력 전송 범위 분리                                       |
| Message               | 작성자, 시각, 대화방 ID, 내용, API/샘플 출처, 모델, 첨부 텍스트 스냅샷 | 응답 생성 시 실제 선택한 모델 보존                                           |

기존 `flowmes-demo-v2` 데이터를 삭제하지 않고 모듈 ID와 기본 대화방 ID를 보완한다. 기존 파일/메시지/체크리스트 ID를 보존한다. 다른 이름의 단계도 동일 moduleId로 분류할 수 있다. 한 업무에 같은 모듈을 여러 번 사용하는 경우 각각 별도 Task 인스턴스다.

## 2. 보드 해석

- 카드 하나는 업무 하나다. 현재 진행 Task의 모듈 열에 한 번만 표시한다. 모든 Task가 완료/건너뜀이면 완료 열로 모은다.
- 현재 단계 필터는 진행 위치, 포함 필터는 업무 구성 전체를 기준으로 한다. 업무에 없는 Task는 대기 단계로 취급하지 않는다.
- 목록과 보드가 검색·상태·담당자·템플릿·모듈 필터를 공유한다.
- 카드의 작은 Task 버튼은 해당 업무의 실제 구성만 보여 주며, 누르면 해당 작업 공간으로 이동한다.
- 모든 Task를 수동으로 구성할 수 있다. 수동 업무도 체크리스트와 자료·메모·진행 상태를 가진다.
- 카드 드래그로 완료 상태를 바꾸지는 않는다. 전환은 작업 공간에서 체크리스트와 전달 자료를 확인하는 기존 절차를 사용한다.

## 3. 사내 API 설정

경로: **워크스페이스 설정 → API 연결 및 모델 관리**.

1. 샘플/API 모드를 선택한다.
2. API 기본 URL에는 서버 주소와 API 접두 경로를 넣는다. 예: `https://llm.example.local/v1`.
3. 대화 경로 `/chat/completions`, 모델 경로 `/models`가 기본 URL 뒤에 붙는다. 실제 설치에 맞게 경로를 변경할 수 있다.
4. API 키는 선택 사항이다. 입력 시 `Authorization: Bearer …`로 전송한다. 키는 React 메모리에만 보관하며 localStorage·파일·리포트에 저장하지 않는다. 새로고침하면 다시 입력한다.
5. 모델 목록은 `GET` 조회 또는 줄 단위 직접 입력을 지원한다. 기본 모델은 목록에 포함되어야 한다. 목록 조회 성공은 모델의 실제 대화 호출 성공을 보장하지 않는다.
6. 모델 적용 순서: **대화방 지정 > 개별 Task 지정 > TaskModule 지정 > 시스템 기본값**. 변경은 다음 요청부터 적용된다. 이전 응답의 모델 기록은 바뀌지 않는다.

호출은 `POST`, `stream:false`, `model`과 `messages`를 보낸다. `choices[0].message.content`의 문자열을 표시한다. 60초 제한, 취소, 네트워크/HTTP/형식 오류를 처리한다. 실패 시 입력 메시지는 보존하고 샘플 응답으로 바꾸지 않는다. 대화방별 요청 잠금은 화면 이동 후에도 유지되며 샘플 데이터 초기화 시 요청을 취소한다.

브라우저 직접 연결이므로 서버가 CORS를 허용해야 한다. 자체 서명 인증서, 사내 VPN, 쿠키 기반 SSO, 프록시 등은 이 데모가 대신 처리하지 않는다. 외부 배포 사이트에서 HTTP 사내 endpoint 접근은 브라우저 정책에 제한될 수 있다. 운영에서는 동일 origin의 사내 gateway와 서버 측 인증을 구성한다.

**OpenWebUI 관련:** assistant 표시 이름과 모델 ID는 서로 다른 설정이다. 기존 skill/knowledge를 사용하려면 설치된 OpenWebUI의 assistant 모델 ID와 endpoint를 지정하고 실제 적용 여부를 확인해야 한다. 기반 LLM의 모델 ID만 사용해도 OpenWebUI의 내부 워크플로우가 실행된다고 가정하지 않는다. 별도의 OpenWebUI chat ID 저장, 서버 측 파일 매핑, tool 실행/stream 응답 처리는 후속 어댑터 범위다.

## 4. 파일 전달 범위

업무 간 파일 연결·다운로드는 기존처럼 원본 ID를 유지한다. 이는 LLM으로 파일을 전송하는 것과 별개다.

- 요청 시 **입력 텍스트 본문을 함께 전달**을 선택하면 text MIME 또는 md/txt/csv/json 파일의 원문을 요청 메시지에 포함한다. 파일당 200KB, 합계 300,000자 제한이다.
- 전송했던 텍스트는 메시지 스냅샷으로 남아 이후 해당 대화방의 이력에 포함된다. 체크를 해제하면 신규 첨부 본문을 추가하지 않으며, 기존 메시지의 첨부 맥락은 유지한다.
- PDF/Office/이미지 등은 전송 제외 개수를 표시한다. 이 파일들의 추출·OCR·지식 연결은 설치 환경의 문서 어댑터가 필요하다.
- 샘플 모드에서는 파일 내용을 분석하지 않는다.

## 5. 여러 참여자가 같은 대화에 참여하는 설계

가능하다. 표준 Chat Completions의 `user` 역할은 한 사람만을 의미하지 않는다. 공식 문서에는 같은 역할의 참여자 구분을 위한 선택적 `name` 필드가 있다: [OpenAI Chat API reference](https://developers.openai.com/api/reference/resources/chat).

데모는 작성자/시각을 플랫폼 데이터로 저장하고, user 메시지 본문에 작성자와 팀 의견/assistant 요청 구분을 덧붙인다. 선택적으로 `name: participant_1` 같은 호환 식별자도 보낸다. 작성자 메타데이터는 모델에게 맥락을 주기 위한 것으로, 인증이나 승인 권한의 근거가 아니다.

대화 UX는 다음과 같다.

1. 팀원이 **팀 의견만 남기기**로 대화 기록을 추가한다. 이때 API 호출은 없다.
2. 누군가 **Assistant 요청**을 보내면 해당 대화방의 이전 팀 의견을 포함하여 한 번 호출한다.
3. 독립 검토가 필요하면 같은 Task에 새로운 대화방을 생성한다. 다른 대화방 메시지는 전달하지 않는다.

현재 작성자 선택은 **한 브라우저에서 체험하는 로컬 데모**다. 두 PC의 동시 참여는 구현하지 않았다. 운영 구현에는 인증된 userId, 공유 메시지 DB, 서버 타임스탬프/순번, 요청 idempotency key, 대화방별 생성 잠금, 재접속 동기화와 WebSocket/SSE 전달이 필요하다. 모델은 실제 승인자를 결정하지 않고, 승인·전자서명은 별도 업무 규칙에서 관리한다.

## 6. 검증 경계

자동 테스트는 모델 우선순위, 데이터 보존 마이그레이션, 모듈 필터, 대화 격리, HTTP 요청 형식과 실패 처리, 요청 초기화를 포함한다. 로컬 브라우저에서 설정·모듈 조합·수동 업무·새로고침 보존 및 실제 HTTP 404 처리를 확인했다. 사내 endpoint/인증 정보는 제공되지 않아 실제 사내 모델 응답과 OpenWebUI skill/knowledge 실행은 미검증이다.
